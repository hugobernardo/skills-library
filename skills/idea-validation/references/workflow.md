# Idea Validation Workflow

## Purpose and session shape

This workflow combines broad ideation with commercial and operational screening for interactive marketing utilities, software-as-marketing, and customer-facing tools whose usefulness, capability demonstration, distribution, and buildability all matter. It is not a general campaign-ideation or product-discovery method.

Default to a guided session with one mandatory alignment gate after the Creative Horizon. Revise and re-present the horizon within that gate until the user approves continuation. After alignment, continue autonomously unless a missing decision would materially change the result. If the user explicitly requests an autonomous run, record assumptions and complete the sequence without pausing.

The full sequence is:

0. Frame the opportunity
1. Expand the Creative Horizon
2. Generate the concept field
3. Force originality
4. Search for magic
5. Test distribution
6. Score the strongest concepts
7. Develop the finalists
8. Name asymmetric winners
9. Run public-example operability proxy tests
10. Re-rank and recommend

The phase numbers describe decision order, not document sections the user must endure. Keep interim outputs readable and avoid repeating complete concept cards when only one field changes.

## Working state

### Working Brief

Record:

- Subject, company, product, or opportunity
- Target audience and any required functional or segment coverage
- Strategic objective
- Desired audience reaction or behavior
- Capability, value proposition, or advantage the ideas should demonstrate
- Preferred build complexity and available resources
- Permitted and prohibited inputs or dependencies
- Creative-risk appetite
- Success criteria and known disqualifiers
- Session mode and requested checkpoints

Separate facts stated by the user from agent assumptions.

### Feasibility labels

Apply these labels wherever inputs matter:

| Label | Meaning |
|---|---|
| `PUBLIC` | Can be obtained from public web pages, public datasets, or open APIs |
| `TYPED` | A user can provide it accurately with little thought |
| `USER-FILE` | Requires the user to locate and upload a non-sensitive artifact |
| `PRIVATE` | Likely confidential, proprietary, personal, or regulated |
| `INTEGRATION` | Requires authentication or access to an internal system |
| `MULTI-USER` | Requires coordinated input from more than one person |

Default to `PUBLIC` and light `TYPED` inputs. `USER-FILE` is acceptable only when the artifact is ordinarily handy and safe to share. Treat `PRIVATE`, `INTEGRATION`, and `MULTI-USER` dependencies as out of scope unless the brief permits them.

### Concept Ledger

Use one row or record per mechanically distinct concept. Track:

- Stable ID and working name
- Territory and target audience
- Core mechanism
- Required inputs and feasibility labels
- User action
- Immediate payoff and output artifact
- Capability demonstrated
- Marketing or adoption mechanism
- Sharing hook
- Build complexity
- Cliché status and replacement history
- Scores, assumptions, and evidence
- Public-example proxy result
- Final disposition

## Phase 0 — Frame the opportunity

Gather only information that changes the search space. A useful opening brief normally covers:

1. What are we generating ideas for?
2. Who should use or care about them?
3. What should the experience make tangible or prove?
4. What commercial, behavioral, or strategic outcome matters?
5. What can the user easily provide, and what is off limits?
6. How much build effort is acceptable?
7. How evenly must the field cover functions, segments, or motivations?
8. How far may the creative risk go?

Ask up to three tightly related clarifying questions when material answers are missing. Reasonable defaults are:

- Broad functional coverage rather than concentrating on the agent's most familiar domain
- Public information plus a few low-effort typed inputs
- No confidential uploads, unavailable operational telemetry, or multiplayer reconciliation
- Most concepts feasible as a prototype by a small team
- High creative latitude, including provocative or absurd ideas with a logical strategic bridge

Do not silently preserve these defaults if the user states otherwise.

### Creative standards

- Prefer products people use over content they merely consume.
- Prefer demonstrating a capability over describing it.
- Prefer a consequential interaction over clever naming or copy.
- Prefer personalized artifacts, discoveries, transformations, scores, or visualizations over generic advice.
- Prefer an inherent distribution loop over promotion added after the fact.
- Prefer one sharp job over a bloated miniature platform.
- Do not assume every idea requires AI, and do not assume a business audience requires a sober experience.
- Do not confuse novelty with value. A strange idea still needs a credible user motivation and payoff.
- Kill mediocre ideas rather than protecting the requested count.

## Phase 1 — Expand the Creative Horizon

Map at least 12 fundamentally different creative territories before presenting specific products. Add territories when needed for real coverage; do not stop at 12 merely because the quota is met.

Organize the map by creative mechanism, not by department, audience segment, or channel. Annotate functional coverage separately. A territory is valid only when it could generate several materially different concepts; a named tool, feature, or departmental use case belongs in Phase 2. Use brief illustrations when needed to make a territory concrete, but label them as illustrations and avoid locking in a product form.

Possible operations include:

- Reveal what people normally cannot see
- Transform or automate a familiar workflow
- Compare the user with peers, competitors, or a counterfactual
- Simulate a future state or downstream consequence
- Reverse-engineer an artifact, decision, or organization
- Convert complexity into a legible map, score, physical metaphor, or visual object
- Stress-test a policy, process, promise, or plan
- Generate a useful artifact from sparse inputs
- Monitor a changing public signal
- Turn work into a game, challenge, experiment, or performance
- Create a personalized report with a genuinely distinctive mechanism
- Create a social object people can use to discuss an uncomfortable truth
- Build a searchable explorer or benchmark from difficult public information
- Stage an industry stunt that produces useful data or proof
- Remove a handoff, approval, or recurring coordination burden
- Let the user experience a before-and-after transformation
- Expose contradictions between public claims, behavior, interfaces, or evidence
- Repurpose an existing public artifact for an unexpected operational job

These are prompts, not a mandatory taxonomy. Merge overlapping territories and invent better ones for the brief.

For every territory provide:

| Field | Requirement |
|---|---|
| Territory | A mechanism-level description, not a product name |
| Why interesting | The motivation, tension, or emotional appeal |
| User action | What the visitor would actually do |
| Accessible inputs | Concrete `PUBLIC` or `TYPED` examples whenever possible |
| Payoff | What becomes easier, clearer, faster, safer, or more entertaining |
| Capability proof | What the experience demonstrates without merely claiming it |
| Sharing logic | The artifact, comparison, utility, or conversation that may travel |
| Constraint fit | Any input, privacy, dependency, or effort concern |

Include several **transform something familiar** illustrations across the required functions. Think in recurring jobs rather than department labels: research an account, audit a URL, plan a week, rewrite a policy, prepare an interview, reconcile a handoff, triage a queue, explain a variance, or turn raw notes into an operating artifact.

After the territory map, add a compact coverage matrix showing which functions or segments each territory could serve. Do not create separate territories merely to fill empty cells.

Run a constraint audit before showing the map:

- Can the necessary inputs be reached publicly or typed without research?
- Would a reasonable user share them?
- Does the territory require hidden response latency, burden, performance, or workflow data?
- Does it depend on multiple people participating?
- Is the output concrete enough to evaluate?
- Is the mechanism genuinely different from the other territories?

Clarify or remove territories that fail these questions. Do not hide dependencies behind phrases such as “analyze company operations.”

**Gate 1:** Show the Creative Horizon and pause. Ask which territories to expand, clarify, reject, or add. Record the response as binding direction for later phases.

## Phase 2 — Generate the concept field

Generate 25 distinct concepts distributed across the surviving territories. Vary them materially across:

- Interaction model
- User motivation
- Emotional appeal and seriousness
- Data source
- Output type
- Distribution mechanism
- Functional audience
- Build model

Do not create minor departmental variants of the same mechanism. If broad functional coverage is required, maintain a coverage matrix, but never sacrifice concept distinctness to make the matrix look tidy.

For each concept provide:

| Field | Requirement |
|---|---|
| Name | A provisional, memorable working name |
| One-line concept | The proposition in one sentence |
| User experience | What someone does from arrival through result |
| Required inputs | Exact inputs with feasibility labels |
| Payoff | The useful, surprising, entertaining, or clarifying result |
| Capability demonstrated | What the underlying organization or product subtly proves |
| Marketing mechanism | How usage creates attention, credibility, or commercial opportunity |
| Sharing hook | Why someone would send, post, cite, compare, or embed it |
| Build complexity | `1` weekend prototype through `5` meaningful product build |

Keep most concepts between complexity 1 and 3 unless the brief calls for more ambition.

## Phase 3 — Force originality

Strip the names from all 25 concepts and compare their mechanisms. Flag:

- Generic ROI calculators
- Generic maturity assessments or quizzes
- Generic AI text generators
- Generic chatbots
- Generic report generators
- Thin wrappers around search or summarization
- The same workflow transplanted between functions
- Outputs whose only purpose is collecting an email address

These forms may survive only when they contain a distinctive interaction, insight, dataset, transformation, or distribution mechanic. Replace weak or derivative concepts so the core field remains 25 strong ideas.

Then add five **wildcards** optimized for memorability rather than stakeholder comfort. Explore ideas that are weird, provocative, playful, unexpectedly useful, highly visual, culturally interesting, or strategically absurd. Each must retain a logical connection to the brief and a credible user payoff.

Record every replacement and rejection reason in the Cliché/Rejection Log.

## Phase 4 — Search for magic

Add five concepts designed around a clear “Wait—it can do that?” moment. Favor mechanisms that:

- Reveal something users normally cannot see
- Transform a familiar artifact into an unexpected useful output
- Compare the user with peers or competitors
- Simulate a future outcome
- Expose an inefficiency, inconsistency, or missed opportunity
- Turn complex information into an instantly legible visualization
- Automate work that normally requires expertise
- Combine fragmented public information into a new inference
- Make a before-and-after difference tangible

For each, state the exact magic moment as an observable interaction or output. “Uses AI” is not a magic moment.

The field now contains 35 concepts unless replacements or justified exclusions change the count. Quality beats quota: disclose if fewer ideas genuinely survive.

## Phase 5 — Apply the hard gate and test distribution

Before selecting candidates for deeper analysis, screen every concept against six hard questions:

1. Are the essential inputs obtainable under the Working Brief?
2. Would a reasonable user provide those inputs?
3. Does the experience return a concrete payoff without requiring a sales conversation?
4. Is its mechanism meaningfully distinct from the remaining field?
5. Can a credible first version fit the permitted build envelope?
6. Is there at least one plausible path through which the product or its output reaches another user?

Reject concepts that fail an essential gate and record the reason. Mark genuinely uncertain cases rather than quietly promoting them. Do not pad the shortlist to 12 if fewer concepts survive.

For the survivors, analyze distribution as product behavior rather than promotional intent:

| Loop | Question |
|---|---|
| Search | Would people naturally search for this job, answer, or artifact? |
| Social | Does the output make an identity signal, visual, surprise, or debate worth posting? |
| Workplace | Would someone send it to a colleague, boss, candidate, customer, or partner to advance real work? |
| Competitive curiosity | Would people compare themselves with a peer, competitor, or benchmark? |
| Embedding | Can another site, community, or publication embed, cite, or reference the output? |
| PR | Is there an aggregate finding, cultural tension, or industry story worth covering? |
| Recurring use | Does changing data or a repeated workflow create a natural return trigger? |

State the primary loop, the artifact that travels, the next recipient, and why that recipient would open it. “People will share the result” is not analysis.

## Phase 6 — Score the strongest concepts

Select up to 12 of the strongest surviving concepts. Score each from 1–10 on:

1. Originality
2. Audience value
3. Capability demonstration
4. Magic moment
5. Shareability
6. Distribution potential
7. Strategic or brand fit
8. Lead or commercial potential
9. Build simplicity

Calculate the unweighted total out of 90 to aid comparison. Add one sentence explaining every unusually high or low score and note the most uncertain assumption.

Use common anchors: `1` means the concept clearly fails the criterion, `5` means plausible but ordinary or substantially unproven, and `10` means exceptional with a concrete mechanism or supporting evidence. Interpolate between them. For Build Simplicity, `10` is a credible weekend prototype and `1` is a major product build.

The total is not the decision. Do not allow several mediocre 7s to automatically defeat an asymmetric idea with a few 10s and one solvable weakness. Preserve at least one risky, non-obvious candidate in the finalist set when it could teach something material.

## Phase 7 — Develop the top seven

Develop the leading seven concepts, or every survivor if fewer than seven remain, using this schema:

| Field | Requirement |
|---|---|
| Concept | Concise explanation |
| Example experience | A realistic path from landing page to result |
| Killer feature | The single interaction or output that makes it memorable |
| Marketing insight | Why the product experience beats an article, ad, or landing page |
| Distribution loop | Exactly how another user discovers it |
| Connection to core capability | Why it prompts “imagine what the real product can do” without becoming a disguised demo |
| CTA | The natural next commercial step, proportional to user intent |
| MVP | The smallest version worth launching |
| Effort | Very Low, Low, Medium, or High |
| Critical assumption | The one uncertainty most likely to break the idea |

## Phase 8 — Name asymmetric winners

Before proxy testing, identify:

- **Best overall:** strongest combination of usefulness, originality, capability proof, and distribution
- **Best low-effort:** smallest credible build with meaningful impact
- **Best viral:** strongest inherent propagation mechanism
- **Most strategically interesting:** less obvious idea with disproportionate long-term potential

Explain why each wins against the closest alternative, not merely why it is good. One concept may win more than one category, but do not force a sweep for narrative neatness.

## Phase 9 — Run public-example operability proxy tests

Run each finalist—normally the top seven—against a relevant public example. This phase tests the mechanism, not the polish.

The proxy can test input availability, likely user effort, output specificity in the chosen case, capability proof, and whether a plausible payoff or magic moment appears. It cannot establish actual user value, output accuracy, implementation feasibility, automation rate, robustness, cost, cross-case generality, market demand, sharing behavior, conversion, acquisition economics, technical scalability, or legal sufficiency. Carry that evidence ceiling into every conclusion. Require two deliberately contrasting examples before making even provisional cross-case claims.

Before gathering data, write a test card for each finalist:

| Field | Requirement |
|---|---|
| Critical hypothesis | The single claim this proxy can meaningfully test |
| Observable success signal | What must appear in the output or process for the claim to survive |
| Falsifier | What result would materially weaken or kill the concept |
| Evidence ceiling | What this test cannot establish |
| Example-selection rule | Why the subject is relevant rather than conveniently flattering |

### Test protocol

1. Choose a relevant real subject and document why it is suitable for this proxy.
2. Acquire only inputs allowed by the Working Brief. List each source and feasibility label.
3. Perform the concept's core analysis, transformation, simulation, or generation as far as available evidence permits.
4. Produce the actual result artifact or a truthful thin slice of it. Do not substitute a description of what the tool would produce.
5. Distinguish observed facts, inferences, and illustrative content.
6. Record unavailable inputs, manual work, brittle steps, latency, and where expert judgment entered.
7. Evaluate whether the output produces a plausible payoff and magic moment in this chosen case.
8. Identify what a coded MVP could automate and what would remain unresolved.

Use authoritative primary sources where practical and cite load-bearing claims. Avoid selecting an example merely because it makes the concept look good. If a concept cannot be meaningfully tested without private data, unavailable telemetry, or multi-user participation, record that failure instead of inventing inputs.

### Public-Example Proxy Log

For each finalist record:

| Field | Requirement |
|---|---|
| Public example | Subject and relevance rationale |
| Inputs obtained | Sources, feasibility labels, and effort |
| Result | The actual thin-slice output |
| What worked | Specific evidence of utility or surprise |
| What failed | Missing data, generic output, weak inference, or operational friction |
| User-input burden | Low, Medium, or High with explanation |
| Transfer risk | Reasons the method may or may not work on other examples; mark untested unless a contrasting second example was run |
| Distribution plausibility | Whether the output contains a credible reason and artifact to travel; not observed sharing behavior |
| MVP implication | What must be built, curated, licensed, or removed |
| Confidence | Low, Medium, or High and why |

## Phase 10 — Re-rank and recommend

Re-score only criteria affected by the proxy. Show the before-and-after position of every finalist and explain each material change.

When the user explicitly requests a build decision, assign one optional disposition within the evidence ceiling:

- **Prototype:** operability supports a narrow interactive prototype whose next job is collecting behavioral evidence
- **Test:** promising, but one cheaper experiment should precede prototyping
- **Hold:** strategically interesting but blocked by cost, data, timing, or dependency
- **Kill:** the proxy found no credible value or operability path, or the distribution hypothesis lacks a plausible artifact and recipient

Conclude with:

- Best overall after proxy evidence
- Best low-effort after proxy evidence
- Strongest distribution hypothesis after proxy evidence
- Most strategically interesting after proxy evidence
- The next behavioral validation required for every `Prototype` recommendation
- The next cheapest experiment for every `Test` recommendation
- Which initial assumptions were wrong
- Which parts remain unvalidated

By default, conclude with the four asymmetric winner categories, changed assumptions, remaining uncertainties, and the next cheapest evidence step. Do not manufacture a winner. A useful outcome may be that none of the finalists deserves further investment yet.

## Optional workflow-conversion extension

Run this only when the user asks whether concepts can become reusable agent skills or workflows. For each requested concept, decide whether it has:

- A repeatable trigger
- Clear, obtainable inputs
- A sequence of decisions or transformations
- A defined output whose quality can be evaluated
- A stable target user
- No essential dependency on inaccessible judgment or data

Return:

- Can become a skill: Yes or No
- Plain-English skill description
- Required inputs
- Expected output
- Target audience
- Proposed skill name
- Blocking dependency or reason for `No`

Do not equate “an agent could discuss this” with “this is a reliable skill.”

## Failure recovery

| Failure | Recovery |
|---|---|
| Territories remain fuzzy | Add exact user action, source, input label, and output |
| Ideas cluster | Strip names, state mechanisms, merge duplicates, then change interaction or data model |
| Concepts require private data | Replace with public proxies or mark the concept out of scope |
| Functions are uneven | Add workflow-first territories in missing functions without copying existing mechanisms |
| Wildcards are merely jokes | Recover a real tension, payoff, or strategic proof from the absurdity |
| Magic depends only on AI | Specify the hidden information, transformation, or expertise being made accessible |
| Distribution is hand-waving | Name the artifact, sender, recipient, motivation, and return path |
| Scores feel decisive without evidence | Surface uncertainty and proceed to the public-example proxy |
| Public example produces generic output | Narrow the job, improve the data, or kill the concept |
| A test requires invented inputs | Stop; missing inputs are the finding |

## Stopping conditions

Stop divergence when the field covers materially different mechanisms, motivations, outputs, and distribution loops—not merely when the requested count is reached.

Stop proxy testing when every finalist has produced an actual thin-slice result or a documented operability failure.

Stop the engagement when the four winner categories have been revisited from proxy evidence, the remaining uncertainties are explicit, and further analysis would cost more than the next real experiment. If the user requested a build decision, also record a bounded disposition for each finalist.
